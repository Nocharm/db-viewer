db-viewer × 여러분의 서비스 · 그림으로 보는 연동 안내

옆 건물 DB를 ‘읽기만’ 하러 가는 길

db-viewer는 여러분 서비스 DB의 구조(테이블·컬럼·관계)를 읽어 지도(ERD)를 그리는 도구입니다. 데이터를 바꾸지 않고, 여러분 서비스의 기존 설정도 건드리지 않습니다.

한 줄로. 두 건물 사이에 복도를 하나 내고(도커 네트워크), 읽기 전용 열쇠 하나를 만들면(DB 계정) 끝입니다. 복도는 미리 지어 둔 공유 복도나 서비스 전용 새 복도 중에서 고릅니다.

버튼을 누르면 내 차례가 아닌 단계는 흐려집니다. 흐름은 그대로 보이니 상대가 무엇을 하는지도 알 수 있습니다.

이 안내서의 낱말

그림에 나오는 비유가 실제로 무엇인지. 이 표만 알면 나머지는 그림대로입니다.

건물 · 방
컨테이너. 여러분 서비스의 앱 컨테이너와 DB 컨테이너.
울타리
default 네트워크. 같은 compose끼리만 통하는 원래 길. 안 건드립니다.
복도
db-viewer용 도커 네트워크. 공유 dbv-shared 또는 전용 dbv-<서비스키>.
문
compose의 networks: 항목 한 줄. 문을 내야 복도로 나갈 수 있습니다.
문패
별칭(alias) <서비스키>-db. 복도에서 여러분 DB를 찾는 이름.
열쇠
읽기 전용 계정 dbviewer_ro. SELECT만 됩니다.
금고 열쇠
SOURCE_SECRET_KEY. db-viewer가 접속 비밀번호를 잠가 두는 키. 처음 한 번.
헐고 다시 짓기
docker compose down / up -d. down은 복도까지 헐어서 쓰지 않습니다.

한 장으로 보면

복도 하나, 열쇠 하나. 복도는 db-viewer 담당자가, 열쇠는 서비스 담당자가 만듭니다. 복도는 두 종류 — 미리 지어 둔 공유 복도(편함, 다른 서비스 DB와 나란히 섬)와 서비스마다 새로 내는 전용 복도(둘만). 여러분 서비스가 원래 쓰던 문(default 네트워크)은 한 줄도 바꾸지 않습니다.

걱정되실 것들 — 먼저 답합니다

우리 데이터를 바꾸나요?

아니요. 열쇠에 SELECT만 줍니다. 여러분 테이블의 INSERT·UPDATE·DELETE는 DB가 거부합니다 (CREATE는 PostgreSQL 15+ 기본에서 거부 — 6단계에서 실제로 확인합니다).

서비스가 느려지나요?

거의 아니요. 평소엔 구조만 읽고, 값은 최대 20행 미리보기입니다.

네트워크 설정이 깨지나요?

기존 것은 그대로. 문을 하나 더 낼 뿐입니다. docker compose down은 쓰지 않습니다.

다른 서비스 DB와 같은 복도에 서나요?

고르기 나름. 전용 복도면 아니요(둘만). 공유 복도면 다른 DB와 문 앞까지 닿습니다(열쇠는 각자). 닿으면 안 되면 전용을 요청하세요.

비밀번호는요?

회신 메일에 그대로 적어 보내면 됩니다. SELECT만 가능한 전용 계정이고, 받은 db-viewer는 금고에 잠가 둡니다(SOURCE_SECRET_KEY).

누가 무엇을 하나

서비스 담당자 여러분 쪽에서

  • DB 방에 창고(볼륨)가 붙어 있는지 확인 (30초)
  • DB 방에 복도 문 하나 내기 (Claude Code가 diff를 만들어 줌)
  • 읽기 전용 열쇠 dbviewer_ro 만들기
  • 회신 명령 한 번 → 출력 그대로 보내기

db-viewer 담당자 우리 쪽에서

  • 복도 고르기(공유/전용) — 전용이면 복도 짓기
  • 금고 열쇠 SOURCE_SECRET_KEY 준비 (처음 한 번)
  • 전용일 때만: db-viewer도 그 복도에 문 내고 backend 재기동
  • 관리 콘솔에 등록 → 연결 테스트 → 수집 → 공개 범위

순서대로 — 열 걸음

번호 색이 곧 담당입니다. 🟩 db-viewer 담당자 → 🟧 서비스 담당자 → 🟩 다시 db-viewer 담당자 순으로 공을 주고받습니다.

  1. 복도 고르고 값 정하기 db-viewer 담당자

    서비스마다 복도를 하나 고릅니다. 둘은 같이 쓸 수 있습니다.

    공유 복도 dbv-shared — 기본

    처음 한 번 지어 두고 db-viewer가 늘 붙어 있는 복도. 대신 같은 복도의 다른 서비스 DB와 문 앞까지 닿습니다(열쇠는 각자). (그림의 svca·svcb·svcc는 예시 서비스 A·B·C입니다.)

    전용 복도 dbv-<서비스키> — 따로

    이 서비스만을 위해 새로 내는 복도. 다른 서비스와 네트워크로 닿으면 안 되는 DB라면 이쪽.

    고른 뒤 아래 표를 채워 서비스 담당자에게 보냅니다. 이름이 어긋나면 나머지가 전부 어긋납니다. 전용이면 복도를 미리 지어 둡니다.

    항목값설명
    복도 방식공유 / 전용기본은 공유. 닿으면 안 되는 DB만 전용
    서비스 키<서비스키>그 서비스를 가리키는 짧은 이름. 소문자·영숫자 (예: payment, inventory). 문패와 전용 복도 이름의 재료
    네트워크 이름dbv-shared (공유) / dbv-<서비스키> (전용)db-viewer 담당자가 만든다 — 공유는 이미 있음
    서브넷 (전용만)10.203.<n>.0/24서비스마다 다른 번호. 0은 공유 복도, 1은 첫 연결이 이미 사용 중이라 2부터 씁니다
    DB compose 서비스명<compose서비스명>예: postgres, db
    문패(별칭)<서비스키>-dbdb-viewer가 이 이름으로 접속. 공유 복도에서는 이 이름만이 여러분 DB를 구별 — 생략 불가
    DB 엔진PostgreSQL / SQLite
    읽기 전용 계정명dbviewer_ro

    [공유] 처음 한 번만 — 이미 있으면 "already exists"가 뜨니 건너뜁니다. 만든 직후 8단계처럼 backend를 한 번 합류시켜 둡니다.

    docker network create --subnet 10.203.0.0/24 dbv-shared

    [전용] 먼저 이미 쓰인 dbv-* 서브넷을 봅니다 — 목록이 비면 아직 하나도 없는 것.

    for n in $(docker network ls --filter name=dbv- --format '{{.Name}}'); do docker network inspect -f '{{.Name}} {{range .IPAM.Config}}{{.Subnet}}{{end}}' "$n"; done
echo "── 사용 중인 dbv- 서브넷 끝 ──"

    [전용] 아래 두 줄만 내 값으로 바꿉니다 — svca는 예시 서비스 키, N은 위 목록에 없는 번호(0=공유, 1=첫 연결이 사용 중이라 2부터). 성공하면 네트워크 ID와 ✅가 찍힙니다.

    SVC_KEY=svca
N=2
docker network create --subnet "10.203.$N.0/24" "dbv-$SVC_KEY" && echo "✅ dbv-$SVC_KEY (10.203.$N.0/24) 생성"
    왜 10.203.x? 사설 대역(RFC1918)이면서 사내 서비스들의 172.36~46, db-viewer 자신의 172.48/16 어디와도 겹치지 않습니다. 0은 공유 복도 몫입니다.

  2. 금고 열쇠 준비 db-viewer 담당자 처음 한 번만

    db-viewer는 접속 비밀번호를 금고에 잠가 둡니다. 금고 열쇠가 SOURCE_SECRET_KEY. 없으면 소스 등록이 503으로 막힙니다.

    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

    출력값을 db-viewer .env의 SOURCE_SECRET_KEY=에 넣고 backend를 재기동합니다.

    한 번 정하면 바꾸지 마세요. 열쇠를 바꾸면 금고 속 비밀번호를 전부 다시 넣어야 합니다.

  3. 값 확인하고 변수로 선언 서비스 담당자 값 입력은 여기서만

    이 절차가 다루는 범위 — 같은 서버의 docker compose로 떠 있는 PostgreSQL/SQLite입니다. DB가 다른 서버에 있거나(RDS 등) MySQL·Oracle이면 아래 자동 감지가 실패합니다. 그 경우 여기서 멈추고 db-viewer 담당자와 방식을 먼저 정하세요.

    이 아래 명령은 전부 여기서 만든 변수를 씁니다. 명령 중간에 이름을 바꿔 넣을 일이 없습니다 — 블록째 복사해 붙여넣으면 됩니다. 한 터미널에서 이어서 실행하세요. 여러 줄짜리 로직은 cat > 파일 <<'SH' … SH로 파일에 저장한 뒤 실행하는 모양입니다 — 붙여넣는 동안 아무것도 실행·치환되지 않아 SSH·tmux 어디서 붙여넣어도 안전합니다. 블록마다 반드시 결과(✅/❌ 또는 값)가 찍힙니다 — 아무 출력이 없다면 붙여넣기가 잘못된 것입니다.

    손으로 채우는 건 두 줄뿐입니다. 둘 다 db-viewer 담당자가 보낸 값을 그대로 옮겨 적습니다. svca는 예시라서 그대로 두면 아래 자가진단이 ❌를 냅니다.

    export DBV_NET=dbv-shared
export SVC_KEY=svca
echo "DBV_NET=$DBV_NET SVC_KEY=$SVC_KEY"
    이 두 값이 어디에 쓰이나.
    • DBV_NET — DB 컨테이너를 추가로 합류시킬 도커 네트워크. 그 네트워크에 든 컨테이너끼리만 서로 보입니다. 호스트 포트를 새로 여는 게 아니라서 사내망·인터넷 쪽 노출은 변하지 않습니다.
    • SVC_KEY — 실제로 붙는 이름은 $SVC_KEY-db, 즉 그 네트워크 안의 별칭(문패)입니다. db-viewer는 IP가 아니라 이 이름으로 접속합니다.

    문패가 지나가는 길 — 한 번 정하면 끝까지 같은 이름으로 따라갑니다.

    SVC_KEY=shop  →  문패 shop-db  →  회신의 "host"  →  관리 콘솔 '호스트' 칸  →  db-viewer가 shop-db:5432로 접속
    보이는 범위. 문패는 그 복도(네트워크) 안에서만 통하는 이름입니다. 다만 공유 복도라면 같은 복도에 있는 다른 서비스의 컨테이너도 이 이름을 조회할 수 있습니다 — 접속은 각자 계정으로 막히지만, 이름이 겹치면 엉뚱한 DB에 붙으므로 서비스마다 다른 키여야 합니다. 이름이 노출되는 것 자체가 곤란한 DB라면 전용 복도를 요청하세요(1단계).

    나머지는 자동입니다 — 자가진단까지 한 번에. 아래 블록은 dbv-setup.sh를 저장하고 바로 실행합니다. 고칠 곳이 없고, 어느 디렉터리에서 실행해도 됩니다: compose 파일이 있는 디렉터리면 그 프로젝트 안에서, 아니면 이 서버 전체에서 DB 컨테이너(postgres 계열 이미지)를 찾고, 찾은 컨테이너의 compose 라벨에서 서비스명·프로젝트 이름·compose 파일 조합(-f 여러 개 포함)을 읽어 COMPOSE_PROJECT_NAME·COMPOSE_FILE로 export 합니다. 이후 이 터미널의 모든 docker compose 명령은 -f/-p 없이도 실제 떠 있는 조합을 그대로 씁니다 — 다른 파일 조합으로 컨테이너가 재생성되는 사고가 원천에서 막힙니다. 관리자 계정·DB명은 컨테이너 env(POSTGRES_USER·POSTGRES_DB)에서 읽고, 비밀번호는 openssl이 만듭니다. 마지막 줄이 bash가 아니라 .(source)인 이유는 변수를 이 터미널에 남기기 위해서입니다.

    cat > dbv-setup.sh <<'SH'
# db-viewer 연동 — 값 자동 감지 + 자가진단
# 변수를 이 터미널에 남겨야 하므로 bash 가 아니라 . (source) 로 실행한다
ok(){ printf '✅ %s\n' "$1"; }
ng(){ printf '❌ %s\n' "$1"; DBV_NG=$((DBV_NG+1)); }
wn(){ printf '⚠️ %s\n' "$1"; }
noise(){ grep -vE '^time=|^WARN'; }
lbl(){ docker inspect -f "{{index .Config.Labels \"$1\"}}" "$DB_CONTAINER" 2>/dev/null; }
env_of(){ docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' "$DB_CONTAINER" 2>/dev/null | sed -n "s/^$1=//p"; }
DBV_NG=0
PG='postgres|postgis|timescale|pgvector'

# 1) DB 컨테이너 — 직접 지정(DB_CONTAINER) > 서비스명 지정(DB_SERVICE) > 자동(현재 디렉터리의 compose 프로젝트 > 이 서버 전체)
PICKED=manual
if [ -n "$DB_CONTAINER" ]; then
  :
elif [ -n "$DB_SERVICE" ]; then
  DB_CONTAINER=$(docker compose ps --format '{{.Name}}' "$DB_SERVICE" 2>/dev/null | head -1)
else
  PICKED=project
  DB_CONTAINER=$(docker compose ps --format '{{.Name}} {{.Image}}' 2>/dev/null | awk -v re="$PG" '$0 ~ re {print $1; exit}')
  if [ -z "$DB_CONTAINER" ]; then
    PICKED=host
    DB_CONTAINER=$(docker ps --format '{{.Names}} {{.Image}}' | awk -v re="$PG" '$0 ~ re {print $1; exit}')
  fi
fi
export DB_CONTAINER

# 2) 실행 중인 컨테이너의 compose 라벨에서 서비스명·프로젝트·파일 조합을 읽어 그대로 재사용
#    이후의 docker compose 명령은 어느 디렉터리에서 쳐도 같은 스택을 가리킨다
s=$(lbl com.docker.compose.service);              [ -n "$s" ] && export DB_SERVICE=$s
p=$(lbl com.docker.compose.project);              [ -n "$p" ] && export COMPOSE_PROJECT_NAME=$p
f=$(lbl com.docker.compose.project.config_files | tr ',' ':'); [ -n "$f" ] && export COMPOSE_FILE=$f

# 3) 관리자 계정·DB명 — 컨테이너 env 가 있으면 그것, 없으면 직접 지정한 값, 그것도 없으면 기본값
v=$(env_of POSTGRES_USER); export DB_SUPER=${v:-${DB_SUPER:-postgres}}
v=$(env_of POSTGRES_DB);   export DB_NAME=${v:-${DB_NAME:-$DB_SUPER}}
export RO_USER=dbviewer_ro
export DB_ALIAS="$SVC_KEY-db"
# 비밀번호는 처음 한 번만 뽑는다 — 다시 실행해도 안 바뀐다
export RO_PASS=${RO_PASS:-$(openssl rand -base64 24)}

# 4) 자가진단
echo "── 자가진단 ──"
if [ -n "$DB_CONTAINER" ] && docker inspect "$DB_CONTAINER" >/dev/null 2>&1; then
  ok "DB 컨테이너   $DB_CONTAINER (서비스 $DB_SERVICE · 프로젝트 ${COMPOSE_PROJECT_NAME:-?})"
else
  ng "DB 컨테이너를 못 찾았습니다 (컨테이너 '$DB_CONTAINER' / 서비스 '$DB_SERVICE') — 아래 '직접 고르기'"
fi
if [ -n "$COMPOSE_FILE" ]; then
  ok "compose 파일  $COMPOSE_FILE"
  [ -n "$COMPOSE_ENV_FILES" ] && ok "env 파일      $COMPOSE_ENV_FILES"
else
  ng "compose 라벨이 없습니다 — docker compose 로 띄운 컨테이너가 아니면 이 안내서 범위 밖입니다"
fi
if docker exec "$DB_CONTAINER" psql -U "$DB_SUPER" -d "$DB_NAME" -Atc 'select 1' >/dev/null 2>&1; then
  ok "DB 접속       $DB_SUPER@$DB_NAME"
else
  ng "psql 접속 실패 ($DB_SUPER@$DB_NAME) — 아래 '직접 고르기'에서 DB_SUPER / DB_NAME 지정"
fi
if docker network inspect "$DBV_NET" >/dev/null 2>&1; then
  ok "복도          $DBV_NET"
else
  ng "네트워크 '$DBV_NET' 이 없습니다 — db-viewer 담당자에게 확인"
fi
case "$SVC_KEY" in
  ''|svca)      ng "서비스 키가 예시값('$SVC_KEY') 그대로입니다 — 받은 값으로 바꾸세요" ;;
  *[!a-z0-9-]*) ng "서비스 키에 소문자·숫자·- 외의 글자가 있습니다 ('$SVC_KEY') — 문패로 못 씁니다" ;;
  *)            ok "서비스 키     $SVC_KEY → 문패 $DB_ALIAS" ;;
esac
n=$(docker compose ps --format '{{.Image}}' 2>/dev/null | grep -cE "$PG")
if [ "$PICKED" = host ]; then
  hn=$(docker ps --format '{{.Image}}' | grep -cE "$PG")
  [ "$hn" -gt 1 ] && wn "현재 디렉터리에 compose 프로젝트가 없어 이 서버 전체에서 골랐습니다 — DB 후보 ${hn}개 중 첫 번째. 프로젝트 이름이 우리 서비스가 맞는지 확인"

  5. DB 방에 복도 문 하나 서비스 담당자

    바꾸는 건 compose 파일뿐(3단계가 찾은 조합 — 여러 개면 그중 하나). 가장 쉬운 길은 3단계의 그 터미널에서 claude를 실행하고 아래 프롬프트를 통째로 붙여넣는 것 — diff를 먼저 보여주고, 승인하면 적용합니다. 같은 터미널이어야 COMPOSE_FILE 등 export 된 값이 Claude Code의 명령에도 전달됩니다.

    손으로 한다면 — 붙여넣을 모양을 터미널이 찍어 줍니다. 내 값이 이미 들어간 채로 나오니 그대로 옮겨 적으면 됩니다. default:는 원래 networks: 키가 없었다면 반드시 함께 적고(아래 함정), aliases는 생략 금지 — 공유 복도에서는 이 이름으로만 구별합니다.

    [ "$DBV_READY" = 1 ] && cat <<EOF || echo "❌ 자가진단(dbv-setup.sh)을 ✅로 통과한 뒤 실행하세요"
services:
  $DB_SERVICE:
    networks:
      default:
      $DBV_NET:
        aliases: [$DB_ALIAS]

  6. 읽기 전용 열쇠 만들기 서비스 담당자

    PostgreSQL: $RO_USER에 SELECT만 줍니다. 비밀번호는 3단계에서 openssl이 이미 만들어 뒀습니다 — 손으로 칠 값이 없습니다. 아래 블록은 dbv-grant.sh를 저장하고 실행합니다: 계정을 만들고(이미 있으면 ALTER ROLE로 비밀번호만 맞춥니다 — 두 번 실행해도 안전), public 스키마에 SELECT를 주고, 읽기는 되고 쓰기는 막히는지까지 바로 확인해 ✅/⚠️/❌로 찍습니다.

    cat > dbv-grant.sh <<'SH'
# db-viewer 연동 — 읽기 전용 계정 만들기 + 읽기/쓰기 확인
[ "$DBV_READY" = 1 ] || { echo "❌ 자가진단(dbv-setup.sh)을 ✅로 통과한 뒤 실행하세요"; exit 1; }
noise(){ grep -vE '^time=|^WARN'; }
psql_super(){ docker exec -i "$DB_CONTAINER" psql -U "$DB_SUPER" -d "$DB_NAME" -v ON_ERROR_STOP=1 "$@"; }
# 읽기 전용 계정은 컨테이너 자기 IP 로 TCP 접속 — 소켓(trust)과 달리 비밀번호가 실제로 검증된다
DB_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' "$DB_CONTAINER" | awk '{print $1}')
psql_ro(){ docker exec -i -e PGPASSWORD="$RO_PASS" -e PGHOST="$DB_IP" "$DB_CONTAINER" psql -U "$RO_USER" -d "$DB_NAME" -v ON_ERROR_STOP=1 "$@"; }

# 계정이 이미 있으면 CREATE 대신 ALTER — 회신에 적힐 비밀번호와 실제를 맞춘다 (두 번 실행해도 안전)
if [ "$(psql_super -Atc "SELECT 1 FROM pg_roles WHERE rolname='$RO_USER'" 2>/dev/null | noise)" = 1 ]; then
  ROLE_SQL="ALTER ROLE $RO_USER LOGIN PASSWORD '$RO_PASS';"
  ROLE_MSG="이미 있던 계정 — 비밀번호만 새로 맞춤"
else
  ROLE_SQL="CREATE ROLE $RO_USER LOGIN PASSWORD '$RO_PASS';"
  ROLE_MSG="새로 만듦"
fi
# ALTER DEFAULT PRIVILEGES: 앞으로 만들어질 테이블에도 자동 적용 — 없으면 마이그레이션 때마다 안 보인다
if psql_super -q <<SQL
$ROLE_SQL
GRANT CONNECT ON DATABASE "$DB_NAME" TO $RO_USER;
GRANT USAGE ON SCHEMA public TO $RO_USER;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO $RO_USER;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO $RO_USER;
SQL
then
  echo "✅ 계정 $RO_USER ($ROLE_MSG) — public 스키마 SELECT 권한 부여"
else
  echo "❌ 계정 만들기 실패 — 위 오류를 db-viewer 담당자에게 알려 주세요"
  exit 1
fi

# 읽기 확인 — public 의 첫 테이블 하나만 (행 수를 세지 않아 큰 테이블에도 부담이 없다)
PROBE_TABLE=$(psql_super -Atc "SELECT quote_ident(table_name) FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE' ORDER BY table_name LIMIT 1" 2>/dev/null | noise)
if [ -n "$PROBE_TABLE" ]; then
  READ_OUT=$(psql_ro -Atc "SELECT count(*) FROM (SELECT 1 FROM public.$PROBE_TABLE LIMIT 1) s" 2>&1 | noise | tail -1)
  case "$READ_OUT" in
    0|1) echo "✅ 읽기 — public.$PROBE_TABLE 조회됨 (비밀번호 검증 포함)" ;;
    *)   echo "❌ 읽기 실패 — $READ_OUT" ;;
  esac
else
  echo "⚠️ 읽기 — public 에 테이블이 아직 없어 건너뜀"
fi
# 쓰기 확인 — 실제로 시도하되 ROLLBACK 이라 아무것도 남지 않는다
WRITE_OUT=$(psql_ro -q -Atc 'BEGIN; CREATE TABLE zzz_probe(id int); ROLLBACK;' 2>&1 | noise)
case "$WRITE_OUT" in
  "") echo "⚠️ 쓰기 — 허용돼 있습니다 (롤백해서 남진 않음 · PG14 이하 public 기본값일 수 있음)" ;;
  *"permission denied"*|*"must be owner"*|*"read-only"*)
      echo "✅ 쓰기 — 차단됨 ($(printf '%s\n' "$WRITE_OUT" | head -1))" ;;
  *)  echo "❓ 쓰기 — 확인 실패 ($(printf '%s\n' "$WRITE_OUT" | head -1))" ;;
esac
SH
bash dbv-grant.sh

    DB가 compose 밖이거나 psql을 직접 쓴다면 psql_super·psql_ro 두 함수의 docker exec … psql 부분만 psql "postgresql://…" 형태로 바꾸면 됩니다.

    마지막 ALTER DEFAULT PRIVILEGES는 그 명령을 실행한 계정($DB_SUPER)이 앞으로 만들 테이블에만 걸립니다. 마이그레이션을 다른 롤로 돌린다면 그 롤을 적어 한 번 더 실행하세요 — ALTER DEFAULT PRIVILEGES FOR ROLE <그 롤> IN SCHEMA public GRANT SELECT ON TABLES TO $RO_USER;

    public 외의 스키마도 보여 주려면 스키마마다 세 줄을 반복합니다. 민감 테이블은 ALL TABLES 대신 테이블을 열거해도 됩니다 — db-viewer 쪽에도 스키마 단위 허용 목록이 따로 있습니다.

    마지막 세 줄 읽는 법 — 읽기·쓰기 확인은 컨테이너 자기 IP로 TCP 접속하므로 비밀번호까지 실제로 검증됩니다(컨테이너 안 소켓 접속은 비밀번호를 묻지 않습니다).

    출력뜻
    ✅ 쓰기 — 차단됨 (ERROR: permission denied for schema public)정상 — 읽기 전용이 제대로 걸렸습니다
    ⚠️ 쓰기 — 허용돼 있습니다PostgreSQL 14 이하는 public 스키마에 누구나 CREATE할 수 있는 게 기본값이라 흔합니다. ROLLBACK이라 테이블은 남지 않았습니다. 막으려면 DB 소유자 판단으로 REVOKE CREATE ON SCHEMA public FROM PUBLIC; — 다른 앱이 그 권한에 기대고 있지 않은지 먼저 확인하세요. 그대로 두어도 db-viewer는 SELECT만 실행합니다
    ❓ 쓰기 — 확인 실패 (… FATAL …) / ❌ 읽기 실패접속 자체가 안 된 것 — 권한 결과가 아닙니다. password authentication failed면 비밀번호가 어긋난 것(3단계 '창을 닫았다면'), 그 외는 계정·DB명·pg_hba.conf를 확인
    ⚠️ 읽기 — public 에 테이블이 아직 없어 건너뜀읽기 확인만 건너뛴 것. 쓰기 확인은 그대로 유효합니다

    SQLite: 열쇠 개념이 없습니다. db-viewer가 창고를 :ro로 마운트하고 파일도 읽기 전용으로 엽니다.

  7. 회신하기 서비스 담당자

    채울 양식이 없습니다. 아래 명령을 붙여넣으면 회신에 필요한 값과 검증 결과가 한 번에 찍힙니다. 터미널에 나온 그대로 복사해 메일로 보내세요.

    비밀번호도 그 안에 그대로 들어 있습니다 — SELECT만 가능한 계정이라 메일 전달을 전제로 만들었습니다. (걱정되면 그 줄만 빼고 따로 알려 주셔도 됩니다.)

    포트는 컨테이너 안쪽 번호(PostgreSQL 기본 5432)입니다. 호스트에 매핑한 바깥 번호가 아닙니다 — db-viewer는 같은 복도 안에서 붙으므로 ports:에 적힌 바깥 번호와는 무관합니다.

  8. db-viewer도 복도에 합류 db-viewer 담당자 전용일 때만

    공유 복도면 이 단계는 없습니다. backend는 이미 dbv-shared에 있습니다. 9단계로 가세요.

    전용 복도(또는 공유 복도를 방금 처음 지은 경우)면 db-viewer의 docker-compose.yml에서 backend에 문을 내고 backend만 재기동합니다. SQLite 소스면 창고도 읽기 전용으로 마운트합니다.

    networks: 목록에 dbv-shared는 한 번, dbv-<서비스키>는 전용 서비스마다 한 항목씩 늘어납니다.

    services:
  backend:
    networks: [dbviewer, dbv-shared, dbv-<서비스키>]
networks:
  dbv-shared: { external: true }
  dbv-<서비스키>: { external: true }

    SQLite 소스라면 창고도 함께 — backend에 volumes: [<볼륨명>:/mnt/sources/<서비스키>:ro], 최상위에 volumes: { <볼륨명>: { external: true, name: <서비스의_볼륨명> } }.

    docker compose up -d backend && docker compose ps backend
    backend가 network … not found로 안 뜨면 1단계 복도가 없는 것입니다. 다시 docker network create.

  9. 관리 콘솔에 등록 db-viewer 담당자

    /admin → 소스·수집 탭. 칸마다 무엇을 넣는지는 아래 ‘칸마다 무엇을’에 그려 두었습니다.

    비밀번호가 두 종류라는 점만 먼저: 칸 상단의 관리 비밀번호는 db-viewer 설정값(PREVIEW_ADMIN_PASSWORD)이고, 폼 안의 접속 비밀번호는 7단계에서 회신받은 dbviewer_ro의 것입니다.

  10. 연결 테스트 → 수집 → 공개 범위 db-viewer 담당자

    • [연결 테스트] — 초록이 떠도 끝이 아닙니다. 응답의 database·version이 회신값과 같은지 눈으로 대조하세요. 흔한 이름(postgres)이 많아 엉뚱한 DB에 붙어도 초록이 뜰 수 있습니다.
    • [카탈로그 수집] — 구조를 읽어 옵니다. 진행률은 같은 탭 아래 수집 잡에 뜹니다.
    • 공개 범위 탭 → 미리보기 허용 스키마 — 등록만으로는 값이 하나도 안 보입니다(기본 전부 차단). 보여 줄 스키마만 골라 허용합니다.
    여기까지 오면 끝. 사용자 화면의 소스 선택기에 새 서비스가 나타납니다.

“스냅샷 N건이 참조하고 있어 삭제할 수 없습니다”가 떴다면 예전 방식의 차단입니다. 지금은 위 확인 상자에서 체크 뒤 함께 삭제하면 됩니다. API를 직접 부른다면 DELETE /api/sources/{id}?cascade=true.

우리 DB를 읽기 전용으로 조회할 예정이야.

## 값
- compose 프로젝트: $COMPOSE_PROJECT_NAME
- compose 파일 (이 조합·이 순서 그대로, 콜론 구분): $COMPOSE_FILE
- env 파일: ${COMPOSE_ENV_FILES:-(따로 없음 — 프로젝트 디렉터리의 .env 가 있으면 자동 적용)}
- 합류시킬 네트워크 이름: $DBV_NET   (이미 docker network create로 만들어져 있음)
- DB 컨테이너의 compose 서비스명: $DB_SERVICE
- DB 컨테이너 이름: $DB_CONTAINER
- 그 네트워크에서 쓸 별칭: $DB_ALIAS   (생략 불가 — 공유 네트워크에서는 이 이름으로만 우리 DB를 찾는다)
- 이 터미널에는 COMPOSE_PROJECT_NAME·COMPOSE_FILE(·COMPOSE_ENV_FILES)이 이미 export 돼 있다.
  docker compose 명령에 -f / -p / --env-file 을 따로 붙이지 말고 그대로 써.

## 반드시 지킬 것
1. 기존 networks 블록의 default 정의(driver, ipam, subnet, gateway)를 절대 수정하지 마.
   subnet을 바꾸면 다른 서비스와 충돌한다. 새 네트워크를 항목으로 "추가"만 해.
2. 이 네트워크에는 우리 DB 컨테이너만 넣어. 앱 등 다른 컨테이너는 넣지 마.
3. docker compose down 은 절대 실행하지 마. 네트워크까지 삭제되어 같은 compose의 다른
   서비스에 영향이 간다. 반영은 docker compose up -d $DB_SERVICE 으로만 해.
4. 애플리케이션 코드, Dockerfile, 의존성은 건드리지 마. 변경은 위 compose 파일 안에서만 —
   파일이 여러 개면 네트워크를 어느 파일에 넣을지 먼저 제안하고 내 승인을 받아.
5. 포트를 호스트로 새로 노출(ports:)하지 마. 같은 네트워크에 있으면 필요 없다.

## 작업 순서
1. 위 compose 파일을 전부 읽고(override 포함), DB 컨테이너가 현재 어떤 네트워크에 붙어
   있는지 보고해.
2. 아래 형태로 수정안을 만들어서 diff를 먼저 보여줘. 내가 승인하면 적용해.

   services:
     $DB_SERVICE:
       networks:
         default:
         $DBV_NET:
           aliases: [$DB_ALIAS]
   networks:
     default:
       ...기존 정의 그대로, 절대 수정 금지...
     $DBV_NET:
       external: true

   주의: 원래 서비스에 networks 키가 없었다면 compose는 default에 자동 연결한다.
   네트워크를 하나라도 명시하는 순간 자동 연결이 사라지므로 default 를 반드시 함께 적어야 한다.
   이걸 빠뜨리면 서비스가 서로 못 찾아서 장애가 난다.

3. 적용 후 docker compose up -d $DB_SERVICE 으로 해당 컨테이너만 재생성해.
4. 검증하고 결과를 보고해:
   - docker inspect -f '{{json .NetworkSettings.Networks}}' $DB_CONTAINER — 기존 네트워크와
     $DBV_NET 둘 다 있는지, 별칭이 붙었는지
   - 우리 서비스가 정상인지 (헬스체크 또는 앱 로그)
   - 기존 default 네트워크의 subnet이 그대로인지: docker network inspect ${COMPOSE_PROJECT_NAME}_default

회신 — 터미널 한 번 서비스 담당자 · 7단계

3단계의 그 터미널에 붙여넣으면 dbv-reply.sh가 저장·실행되어 회신 값과 검증 결과(네트워크·별칭·읽기·쓰기 차단·서비스 상태)가 한 번에 찍힙니다. 찍힌 내용을 그대로 복사해 db-viewer 담당자에게 메일로 보내세요. compose가 stderr로 찍는 경고(time=…/WARN…)는 판정에서 걸러 냅니다.

cat > dbv-reply.sh <<'SH'
# db-viewer 연동 — 회신 내용 + 검증 결과를 한 번에 출력
[ "$DBV_READY" = 1 ] || { echo "❌ 자가진단(dbv-setup.sh)을 ✅로 통과한 뒤 실행하세요"; exit 1; }
noise(){ grep -vE '^time=|^WARN'; }
psql_super(){ docker exec -i "$DB_CONTAINER" psql -U "$DB_SUPER" -d "$DB_NAME" -v ON_ERROR_STOP=1 "$@"; }
# 읽기 전용 계정은 컨테이너 자기 IP 로 TCP 접속 — 소켓(trust)과 달리 비밀번호가 실제로 검증된다
DB_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' "$DB_CONTAINER" | awk '{print $1}')
psql_ro(){ docker exec -i -e PGPASSWORD="$RO_PASS" -e PGHOST="$DB_IP" "$DB_CONTAINER" psql -U "$RO_USER" -d "$DB_NAME" -v ON_ERROR_STOP=1 "$@"; }

NETS=$(docker inspect -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}' "$DB_CONTAINER")
ALIAS_OK=$(docker inspect -f "{{(index .NetworkSettings.Networks \"$DBV_NET\").Aliases}}" "$DB_CONTAINER" 2>/dev/null)
ALIAS_OK=${ALIAS_OK:-"❌ 아직 $DBV_NET 에 안 붙었습니다 (compose 에 문을 아직 안 냈습니다)"}
PROBE_TABLE=$(psql_super -Atc "SELECT quote_ident(table_name) FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE' ORDER BY table_name LIMIT 1" 2>/dev/null | noise)
if [ -n "$PROBE_TABLE" ]; then
  READ_OUT=$(psql_ro -Atc "SELECT count(*) FROM (SELECT 1 FROM public.$PROBE_TABLE LIMIT 1) s" 2>&1 | noise | tail -1)
  case "$READ_OUT" in
    0|1) READ_OK="✅ public.$PROBE_TABLE 조회됨 (비밀번호 검증 포함)" ;;
    *)   READ_OK="❌ $READ_OUT" ;;
  esac
else
  READ_OK="⚠ public 에 테이블이 없어 건너뜀"
fi
WRITE_OUT=$(psql_ro -q -Atc 'BEGIN; CREATE TABLE zzz_probe(id int); ROLLBACK;' 2>&1 | noise)
case "$WRITE_OUT" in
  "") WRITE_BLOCKED="⚠ 쓰기가 허용돼 있습니다 (롤백해서 남진 않음 · PG14 이하 public 기본값일 수 있음)" ;;
  *"permission denied"*|*"must be owner"*|*"read-only"*)
      WRITE_BLOCKED="✅ 차단됨 — $(printf '%s\n' "$WRITE_OUT" | head -1)" ;;
  *)  WRITE_BLOCKED="❓ 확인 실패 — $(printf '%s\n' "$WRITE_OUT" | head -1)" ;;
esac
SVC_STATUS=$(docker compose ps --format '{{.Service}} {{.Status}}' 2>/dev/null | noise | tr '\n' ' ')
SCHEMAS=$(psql_super -Atc "SELECT string_agg(DISTINCT table_schema, ', ') FROM information_schema.role_table_grants WHERE grantee='$RO_USER'" 2>/dev/null | noise)

cat <<EOF
──── db-viewer 연동 회신 ────────────────────────
서비스 키:        $SVC_KEY
엔진:             PostgreSQL
네트워크:          $DBV_NET
host (별칭):      $DB_ALIAS
포트:             5432        (컨테이너 안쪽 번호)
DB명:             $DB_NAME
계정:             $RO_USER
비밀번호:          $RO_PASS
조회 대상 스키마:   ${SCHEMAS:-public}

검증
- 붙어 있는 네트워크: $NETS
- 별칭:             $ALIAS_OK
- 읽기 확인:         $READ_OK
- 쓰기 차단 확인:    $WRITE_BLOCKED
- 서비스 상태:      ${SVC_STATUS:-(docker compose ps 로 직접 확인해 적어 주세요)}
─────────────────────────────────────────────
EOF
SH
bash dbv-reply.sh

회신을 보냈으면 그 디렉터리에 남은 dbv-setup.sh·dbv-grant.sh·dbv-reply.sh는 지워도 됩니다 — 값은 전부 터미널 변수에서 오므로 파일 안에는 비밀번호가 없습니다.

SQLite라면 네트워크·계정이 없으니 이 블록으로 대신합니다. 첫 두 줄은 예시입니다 — 볼륨이 마운트된 디렉터리와 그 안의 DB 파일을 실제 경로로 바꾸세요.

export SQLITE_DIR=/app/data
export SQLITE_PATH="$SQLITE_DIR/app.db"
cat > dbv-reply-sqlite.sh <<'SH'
# db-viewer 연동 (SQLite) — 회신 내용 출력
[ -n "$DB_CONTAINER" ] && [ -n "$SVC_KEY" ] || { echo "❌ 값 두 줄과 dbv-setup.sh 를 먼저 실행하세요"; exit 1; }
[ -n "$SQLITE_DIR" ] && [ -n "$SQLITE_PATH" ] || { echo "❌ SQLITE_DIR / SQLITE_PATH 를 먼저 export 하세요"; exit 1; }
SQLITE_VOL=$(docker inspect -f "{{range .Mounts}}{{if eq .Destination \"$SQLITE_DIR\"}}{{.Name}}{{end}}{{end}}" "$DB_CONTAINER")
[ -n "$SQLITE_VOL" ] || echo "⚠ 볼륨을 못 찾았습니다 — SQLITE_DIR 이 실제 마운트 지점인지 확인"
JOURNAL=$(docker exec "$DB_CONTAINER" sqlite3 "$SQLITE_PATH" 'PRAGMA journal_mode;' 2>/dev/null) || JOURNAL=""
cat <<EOF
──── db-viewer 연동 회신 (SQLite) ───────────────
서비스 키:        $SVC_KEY
엔진:             SQLite
볼륨 이름:         ${SQLITE_VOL:-❌ 못 찾음}
컨테이너 내부 경로: $SQLITE_PATH
저널 모드:         ${JOURNAL:-(확인 못 함 — 컨테이너에 sqlite3가 없으면 공란)}
─────────────────────────────────────────────
EOF
SH
bash dbv-reply-sqlite.sh
저널 모드가 wal로 나오면 읽기 전용 열기가 실패할 수 있습니다. 그대로 회신에 적어 주세요 — db-viewer 담당자가 등록 전에 확인합니다.
