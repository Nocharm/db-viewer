db-viewer × 여러분의 서비스 · 그림으로 보는 연동 안내

옆 건물 DB를 ‘읽기만’ 하러 가는 길

db-viewer는 여러분 서비스 DB의 구조(테이블·컬럼·관계)를 읽어 지도(ERD)를 그리는 도구입니다. 데이터를 바꾸지 않고, 여러분 서비스의 기존 설정도 건드리지 않습니다.

한 줄로. 두 건물 사이에 복도를 하나 내고(도커 네트워크), 읽기 전용 열쇠 하나를 만들면(DB 계정) 끝입니다. 복도는 미리 지어 둔 공유 복도나 서비스 전용 새 복도 중에서 고릅니다.

버튼을 누르면 내 차례가 아닌 단계는 흐려집니다. 흐름은 그대로 보이니 상대가 무엇을 하는지도 알 수 있습니다.

이 안내서의 낱말

그림에 나오는 비유가 실제로 무엇인지. 이 표만 알면 나머지는 그림대로입니다.

건물 · 방
컨테이너. 여러분 서비스의 앱 컨테이너와 DB 컨테이너.
울타리
default 네트워크. 같은 compose끼리만 통하는 원래 길. 안 건드립니다.
복도
db-viewer용 도커 네트워크. 공유 dbv-shared 또는 전용 dbv-<서비스키>.
문
compose의 networks: 항목 한 줄. 문을 내야 복도로 나갈 수 있습니다.
문패
별칭(alias) <서비스키>-db. 복도에서 여러분 DB를 찾는 이름.
열쇠
읽기 전용 계정 dbviewer_ro. SELECT만 됩니다.
금고 열쇠
SOURCE_SECRET_KEY. db-viewer가 접속 비밀번호를 잠가 두는 키. 처음 한 번.
헐고 다시 짓기
docker compose down / up -d. down은 복도까지 헐어서 쓰지 않습니다.

한 장으로 보면

복도 하나, 열쇠 하나. 복도는 db-viewer 담당자가, 열쇠는 서비스 담당자가 만듭니다. 복도는 두 종류 — 미리 지어 둔 공유 복도(편함, 다른 서비스 DB와 나란히 섬)와 서비스마다 새로 내는 전용 복도(둘만). 여러분 서비스가 원래 쓰던 문(default 네트워크)은 한 줄도 바꾸지 않습니다.

걱정되실 것들 — 먼저 답합니다

우리 데이터를 바꾸나요?

아니요. 열쇠에 SELECT만 줍니다. CREATE·UPDATE는 DB가 거부합니다.

서비스가 느려지나요?

거의 아니요. 평소엔 구조만 읽고, 값은 최대 20행 미리보기입니다.

네트워크 설정이 깨지나요?

기존 것은 그대로. 문을 하나 더 낼 뿐입니다. docker compose down은 쓰지 않습니다.

다른 서비스 DB와 같은 복도에 서나요?

고르기 나름. 전용 복도면 아니요(둘만). 공유 복도면 다른 DB와 문 앞까지 닿습니다(열쇠는 각자). 닿으면 안 되면 전용을 요청하세요.

비밀번호는요?

문서에 안 씁니다. 별도 보안 채널로 전달하고, db-viewer는 금고에 잠가 둡니다.

누가 무엇을 하나

서비스 담당자 여러분 쪽에서

  • DB 방에 창고(볼륨)가 붙어 있는지 확인 (30초)
  • DB 방에 복도 문 하나 내기 (Claude Code가 diff를 만들어 줌)
  • 읽기 전용 열쇠 dbviewer_ro 만들기
  • 회신 양식 채워 보내기

db-viewer 담당자 우리 쪽에서

  • 복도 고르기(공유/전용) — 전용이면 복도 짓기
  • 금고 열쇠 SOURCE_SECRET_KEY 준비 (처음 한 번)
  • 전용일 때만: db-viewer도 그 복도에 문 내고 backend 재기동
  • 관리 콘솔에 등록 → 연결 테스트 → 수집 → 공개 범위

순서대로 — 아홉 걸음

번호 색이 곧 담당입니다. 🟩 db-viewer 담당자 → 🟧 서비스 담당자 → 🟩 다시 db-viewer 담당자 순으로 공을 주고받습니다.

  1. 복도 고르고 값 정하기 db-viewer 담당자

    서비스마다 복도를 하나 고릅니다. 둘은 같이 쓸 수 있습니다.

    공유 복도 dbv-shared — 기본

    처음 한 번 지어 두고 db-viewer가 늘 붙어 있는 복도. 대신 같은 복도의 다른 서비스 DB와 문 앞까지 닿습니다(열쇠는 각자).

    전용 복도 dbv-<서비스키> — 따로

    이 서비스만을 위해 새로 내는 복도. 다른 서비스와 네트워크로 닿으면 안 되는 DB라면 이쪽.

    고른 뒤 아래 표를 채워 서비스 담당자에게 보냅니다. 이름이 어긋나면 나머지가 전부 어긋납니다. 전용이면 복도를 미리 지어 둡니다.

    항목값설명
    복도 방식공유 / 전용기본은 공유. 닿으면 안 되는 DB만 전용
    서비스 키<서비스키>소문자·영숫자. 예: svca
    네트워크 이름dbv-shared (공유) / dbv-<서비스키> (전용)db-viewer 담당자가 만든다 — 공유는 이미 있음
    서브넷 (전용만)10.203.<n>.0/24<n>은 1부터 서비스마다 다르게. 0은 공유 복도, 1은 첫 연결이 이미 사용 — 다음은 2, 3, …
    DB compose 서비스명<compose서비스명>예: postgres, db
    문패(별칭)<서비스키>-dbdb-viewer가 이 이름으로 접속. 공유 복도에서는 이 이름만이 여러분 DB를 구별 — 생략 불가
    DB 엔진PostgreSQL / SQLite
    읽기 전용 계정명dbviewer_ro
     
    # [공유] 처음 한 번만 — 이미 있으면 건너뜀. 만든 직후 7단계처럼 backend를 한 번 합류시켜 둔다
docker network create --subnet 10.203.0.0/24 dbv-shared

# [전용] 서비스마다 — 이미 쓰인 <n> 확인
docker network ls --filter name=dbv- --format '{{.Name}}' \
  | xargs -I{} docker network inspect -f '{{.Name}} {{range .IPAM.Config}}{{.Subnet}}{{end}}' {}

# [전용] 비어 있는 <n>으로 만들기 (예: 두 번째 서비스 → 10.203.2.0/24)
docker network create --subnet 10.203.<n>.0/24 dbv-<서비스키>
    왜 10.203.x? 사설 대역(RFC1918)이면서 사내 서비스들의 172.36~46, db-viewer 자신의 172.48/16, 개발 스택 172.49/16 어디와도 겹치지 않습니다. 0은 공유 복도 몫입니다.

  2. 금고 열쇠 준비 db-viewer 담당자 처음 한 번만

    db-viewer는 접속 비밀번호를 금고에 잠가 둡니다. 금고 열쇠가 SOURCE_SECRET_KEY. 없으면 소스 등록이 503으로 막힙니다.

    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

    출력값을 db-viewer .env의 SOURCE_SECRET_KEY=에 넣고 backend를 재기동합니다.

    한 번 정하면 바꾸지 마세요. 열쇠를 바꾸면 금고 속 비밀번호를 전부 다시 넣어야 합니다.

  3. 창고(볼륨) 확인 서비스 담당자 건너뛰면 안 됨

    docker inspect -f '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{"\n"}}{{end}}' <DB컨테이너명>

    예: volume pgdata -> /var/lib/postgresql/data 처럼 보이면 다음 단계. 비어 있으면 연결보다 창고 붙이기가 먼저입니다.

  4. DB 방에 복도 문 하나 서비스 담당자

    바꾸는 파일은 docker-compose.yml 하나. 가장 쉬운 길은 저장소 루트에서 claude를 실행하고 아래 프롬프트를 통째로 붙여넣는 것 — diff를 먼저 보여주고, 승인하면 적용합니다.

    손으로 한다면 결과는 이 모양입니다:

    services:
  <compose서비스명>:
    networks:
      default:                  # ← 원래 networks 키가 없었다면 반드시 함께 적는다
      <네트워크이름>:            # dbv-shared 또는 dbv-<서비스키> (1단계 값)
        aliases: [<서비스키>-db]  # 생략 금지 — 공유 복도에서는 이 이름으로만 구별
networks:
  default:
    ...기존 정의 그대로, 수정 금지...
  <네트워크이름>:
    external: true
    함정 하나. 원래 networks: 키가 없던 서비스는 default에 자동으로 붙어 있었습니다. 문을 하나라도 적는 순간 자동 연결이 사라지므로 default:를 반드시 같이 적어야 합니다. 빠뜨리면 서비스끼리 서로를 못 찾습니다.
    docker compose up -d <compose서비스명>

# 확인: 기존 네트워크 + <네트워크이름> 둘 다 보이고 별칭이 붙었는지
docker inspect -f '{{json .NetworkSettings.Networks}}' <DB컨테이너명>

    SQLite라면 이 단계는 필요 없습니다 — 창고(볼륨) 이름과 컨테이너 안 파일 경로만 6단계에서 알려 주세요.

  5. 읽기 전용 열쇠 만들기 서비스 담당자

    PostgreSQL: dbviewer_ro에 SELECT만 줍니다. 비밀번호는 직접 만듭니다 (예: openssl rand -base64 24).

    -- <강력한 비밀번호>는 직접 생성한다 (예: openssl rand -base64 24)
CREATE ROLE dbviewer_ro LOGIN PASSWORD '<강력한 비밀번호>';

GRANT CONNECT ON DATABASE <DB명> TO dbviewer_ro;
GRANT USAGE ON SCHEMA public TO dbviewer_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbviewer_ro;

-- 앞으로 만들어질 테이블에도 자동 적용 — 이게 없으면 마이그레이션 때마다 안 보인다
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO dbviewer_ro;

    public 외의 스키마도 보여 주려면 스키마마다 세 줄을 반복합니다. 민감 테이블은 ALL TABLES 대신 테이블을 열거해도 됩니다 — db-viewer 쪽에도 스키마 단위 허용 목록이 따로 있습니다.

    만들고 나서 꼭 확인: 다른 세션에서 dbviewer_ro로 접속해

    SELECT count(*) FROM <아무 테이블>;          -- 성공해야 한다
CREATE TABLE zzz_probe (id int);            -- 반드시 권한 오류가 나야 한다

    SQLite: 열쇠 개념이 없습니다. db-viewer가 창고를 :ro로 마운트하고 파일도 읽기 전용으로 엽니다.

  6. 회신하기 서비스 담당자

    아래 양식을 채워 db-viewer 담당자에게 보냅니다. 비밀번호만은 이 문서·메일이 아니라 별도 보안 채널로.

    포트는 컨테이너 안쪽 번호(PostgreSQL 기본 5432)입니다. 호스트에 매핑한 바깥 번호가 아닙니다 — 8단계 그림 참고.

  7. db-viewer도 복도에 합류 db-viewer 담당자 전용일 때만

    공유 복도면 이 단계는 없습니다. backend는 이미 dbv-shared에 있습니다. 8단계로 가세요.

    전용 복도(또는 공유 복도를 방금 처음 지은 경우)면 db-viewer의 docker-compose.yml에서 backend에 문을 내고 backend만 재기동합니다. SQLite 소스면 창고도 읽기 전용으로 마운트합니다.

    services:
  backend:
    networks: [dbviewer, dbv-shared, dbv-<서비스키>]   # dbv-shared는 한 번, dbv-<서비스키>는 전용 서비스마다
    # SQLite 소스라면:
    # volumes: [<볼륨명>:/mnt/sources/<서비스키>:ro]
networks:
  dbv-shared: { external: true }
  dbv-<서비스키>: { external: true }
# volumes:
#   <볼륨명>: { external: true, name: <서비스의_볼륨명> }
    docker compose up -d backend
    backend가 network … not found로 안 뜨면 1단계 복도가 없는 것입니다. 다시 docker network create.

  8. 관리 콘솔에 등록 db-viewer 담당자

    /admin → 소스·수집 탭. 칸마다 무엇을 넣는지는 아래 ‘칸마다 무엇을’에 그려 두었습니다.

    비밀번호가 두 종류라는 점만 먼저: 칸 상단의 관리 비밀번호는 db-viewer 설정값(PREVIEW_ADMIN_PASSWORD)이고, 폼 안의 접속 비밀번호는 6단계에서 회신받은 dbviewer_ro의 것입니다.

  9. 연결 테스트 → 수집 → 공개 범위 db-viewer 담당자

    • [연결 테스트] — 초록이 떠도 끝이 아닙니다. 응답의 database·version이 회신값과 같은지 눈으로 대조하세요. 흔한 이름(postgres)이 많아 엉뚱한 DB에 붙어도 초록이 뜰 수 있습니다.
    • [카탈로그 수집] — 구조를 읽어 옵니다. 진행률은 같은 탭 아래 수집 잡에 뜹니다.
    • 공개 범위 탭 → 미리보기 허용 스키마 — 등록만으로는 값이 하나도 안 보입니다(기본 전부 차단). 보여 줄 스키마만 골라 허용합니다.
    여기까지 오면 끝. 사용자 화면의 소스 선택기에 새 서비스가 나타납니다.

관리 콘솔, 칸마다 무엇을 넣나

db-viewer 담당자 8단계에서 보는 등록 폼입니다. 왼쪽 번호 순서로 채우고, 값을 어디서 확인하는지는 아래 표에 있습니다.

0관리 비밀번호•••••••• (db-viewer .env의 PREVIEW_ADMIN_PASSWORD) 폼 위의 별도 칸. 접속 비밀번호와 다른 값입니다. 이게 비면 등록·수정·삭제 버튼이 잠깁니다.
1이름svca 사용자에게 보이는 소스 이름. 서비스 키를 그대로 쓰면 헷갈리지 않습니다.
2엔진PostgreSQL ▾ PostgreSQL / SQLite. 만든 뒤에는 못 바꿉니다(바꾸려면 새로 등록).
3호스트svca-db = 문패(별칭) <서비스키>-db. IP도, 호스트 이름도 아닙니다.
4포트5432 = 컨테이너 안쪽 포트. compose의 ports: "15432:5432"라면 뒤쪽 5432.
5databasebilling 회신받은 DB명. 연결 테스트 응답의 database와 같아야 합니다.
6읽기전용 계정dbviewer_ro
7접속 비밀번호•••••••• (보안 채널로 받은 값) 저장 후 화면에 다시 보이지 않습니다. 수정 폼에서 비워 두면 기존 값 유지.
S(SQLite) 파일 경로/mnt/sources/svcc/app.db backend 컨테이너 안에서 보이는 경로 — 7단계에서 마운트한 위치 + 회신받은 파일명.
칸값을 어디서 확인하나
3 호스트(문패)서비스 담당자의 회신 ‘네트워크 별칭’. 직접 보려면 서비스 서버에서 docker inspect -f '{{json .NetworkSettings.Networks}}' <DB컨테이너명> → dbv-shared(또는 dbv-<서비스키>) 항목의 Aliases
4 포트서비스 compose의 DB ports: 뒤쪽 숫자, 또는 docker inspect -f '{{json .Config.ExposedPorts}}' <DB컨테이너명> → 예: {"5432/tcp":{}}
5 database회신 ‘DB명’. 직접 보려면 docker exec <DB컨테이너명> psql -U postgres -c '\l', 또는 compose의 POSTGRES_DB
6 계정 / 7 비밀번호5단계에서 만든 dbviewer_ro. 비밀번호는 보안 채널로 받은 값

완전히 지우기 = 삭제

[삭제]를 누르면 함께 사라지는 것이 먼저 나열됩니다 — 수집 스냅샷, 미리보기 허용 스키마, 스키마 카테고리, 값 추적 잡. “확인했습니다”에 체크해야 [함께 삭제]가 열립니다. 되돌릴 수 없습니다.

“스냅샷 N건이 참조하고 있어 삭제할 수 없습니다”가 떴다면 예전 방식의 차단입니다. 지금은 위 확인 상자에서 체크 뒤 함께 삭제하면 됩니다. API를 직접 부른다면 DELETE /api/sources/{id}?cascade=true.

서비스 담당자 여러분 쪽에서 할 일은 없습니다. 원하면 compose에서 그 복도(dbv-shared 또는 dbv-<서비스키>) 문을 지우고 그 컨테이너만 다시 올리면 복도가 닫힙니다(역시 down은 쓰지 않습니다).

Claude Code 프롬프트 서비스 담당자 · 4단계

저장소 루트에서 claude를 실행한 뒤 아래를 통째로 붙여넣습니다. <...>는 1단계 값으로 미리 바꿔 두세요.

우리 서비스의 docker-compose.yml을 수정해서, DB 컨테이너를 외부에서 이미 만들어 둔
db-viewer용 브리지 네트워크에 "추가로" 합류시켜 줘. 사내 db-viewer가 이 네트워크를 통해
우리 DB를 읽기 전용으로 조회할 예정이야.

## 값
- 합류시킬 네트워크 이름: <네트워크이름>   (dbv-shared 또는 dbv-<서비스키> — 이미 `docker network create`로 만들어져 있음)
- DB 컨테이너의 compose 서비스명: <compose서비스명>
- 그 네트워크에서 쓸 별칭: <서비스키>-db   (생략 불가 — 공유 네트워크에서는 이 이름으로만 우리 DB를 찾는다)

## 반드시 지킬 것
1. 기존 `networks:` 블록의 `default` 정의(driver, ipam, subnet, gateway)를 절대 수정하지 마.
   subnet을 바꾸면 다른 서비스와 충돌한다. 새 네트워크를 항목으로 "추가"만 해.
2. 이 네트워크에는 우리 DB 컨테이너만 넣어. 앱 등 다른 컨테이너는 넣지 마.
3. `docker compose down`은 절대 실행하지 마. 네트워크까지 삭제되어 같은 compose의 다른
   서비스에 영향이 간다. 반영은 `docker compose up -d <compose서비스명>` 으로만 해.
4. 애플리케이션 코드, Dockerfile, 의존성은 건드리지 마. 변경은 docker-compose.yml 하나뿐이어야 한다.
5. 포트를 호스트로 새로 노출(`ports:`)하지 마. 같은 네트워크에 있으면 필요 없다.

## 작업 순서
1. docker-compose.yml을 읽고, DB 컨테이너가 현재 어떤 네트워크에 붙어 있는지 보고해.
   compose 파일이 여러 개면(override 포함) 전부 확인해.
2. 아래 형태로 수정안을 만들어서 diff를 먼저 보여줘. 내가 승인하면 적용해.

   services:
     <compose서비스명>:
       networks:
         default:                  # 기존 그대로 (원래 networks 키가 없었다면 default를 명시적으로 추가)
         <네트워크이름>:
           aliases: [<서비스키>-db]
   networks:
     default:
       ...기존 정의 그대로, 절대 수정 금지...
     <네트워크이름>:
       external: true

   주의: 원래 서비스에 `networks:` 키가 없었다면 compose는 default에 자동 연결한다.
   네트워크를 하나라도 명시하는 순간 자동 연결이 사라지므로 `default:`를 반드시 함께 적어야 한다.
   이걸 빠뜨리면 서비스가 서로 못 찾아서 장애가 난다.

3. 적용 후 `docker compose up -d <compose서비스명>` 으로 해당 컨테이너만 재생성해.
4. 검증하고 결과를 보고해:
   - `docker inspect -f '{{json .NetworkSettings.Networks}}' <DB컨테이너명>` — 기존 네트워크와
     <네트워크이름> 둘 다 있는지, 별칭이 붙었는지
   - 우리 서비스가 정상인지 (헬스체크 또는 앱 로그)
   - 기존 default 네트워크의 subnet이 그대로인지: `docker network inspect <프로젝트>_default`

작업 중 위 "반드시 지킬 것"과 충돌하는 상황이 나오면 진행하지 말고 나에게 물어봐.
